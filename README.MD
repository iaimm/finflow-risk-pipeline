我先按你想说的是“**攻关学习**”来安排：以截图中的**数据工程师岗位要求**为目标，用一个月集中提升 Python 后端、REST API、SQL、ETL 和大数据处理能力。

先说明预期：一个月不可能真正“精通”所有技术，但可以做到**核心知识能讲清楚、常见面试题能回答、手头有一个可演示的完整项目**。考虑到你的时间比较碎片化，下面每天同时给出标准任务和极简完成方式。

## 一、学习路线：只做一个项目，串起全部考点

建议技术栈：

- **核心必学**：Python、FastAPI、PostgreSQL、SQLAlchemy、Pytest、ETL、PySpark。
- **了解即可**：Kafka、微服务拆分、Docker。
- **加分项二选一**：Azure ADF＋Databricks，或 DataWorks＋MaxCompute。
- **暂不投入**：同时学习 Kafka、Flink、Spark，或深入研究 Kubernetes。

贯穿全月的项目定为：

> **金融交易数据管道与风险报表系统**

数据来源使用自己生成的客户、账户、交易 CSV／JSON 数据，最终完成：

```text
CSV／JSON／模拟外部 API
        ↓
原始数据层 Raw
        ↓  校验、去重、清洗、异常隔离
标准数据层 Clean
        ↓  PySpark 汇总与风险规则计算
报表数据层 Mart
        ↓
FastAPI 查询接口＋JWT 鉴权
        ↓
每日交易报表／异常交易清单
```

金融规则仅用于技术练习，不对应真实监管或反洗钱口径。

每天标准学习时间为 **90～120 分钟**：

1. 20 分钟：学习当天概念。
2. 60～70 分钟：动手写代码。
3. 15 分钟：测试、破坏场景、修复问题。
4. 5～10 分钟：记录“今天做了什么、遇到什么问题、如何解释”。

只有 30 分钟时，不重新看课程，直接完成当天任务中的**最小可交付成果**。

## 二、第一周：Python 工程化与 REST API

目标：摆脱“会写脚本”，展示结构化、可复用、可测试的后端能力。

| 天数 | 学习重点 | 实操任务与验收标准 |
|---|---|---|
| 第1天 | 环境、差距评估、项目骨架 | 建立项目目录，区分 `api`、`services`、`repositories`、`models`、`pipelines`、`tests`；生成模拟客户、账户和交易数据。**极简版**：只建目录并生成100条交易数据。 |
| 第2天 | Python OOP、数据类、抽象与组合 | 建立 `Customer`、`Account`、`Transaction` 模型；用数据类减少模板代码；定义交易服务和仓储接口。重点理解“何时用类”，不要为了 OOP 而 OOP。 |
| 第3天 | 可维护代码 | 加入类型标注、统一异常、日志、配置管理；用 Pytest 测试正常、边界和异常输入；掌握依赖注入的基本思想。 |
| 第4天 | REST API 设计 | 用 FastAPI 实现创建交易、查询单笔交易、分页查询交易；明确 200、201、400／422、404、409 的使用场景；使用 Pydantic 校验请求。 |
| 第5天 | 接口鉴权与安全 | 实现登录和 JWT 访问令牌；区分认证与授权；给报表接口增加角色限制；验证无效令牌、过期令牌、无权限访问。密码需哈希，密钥不得写死。 |
| 第6天 | 数据库接入与分层 | 用 SQLAlchemy 接入 PostgreSQL；API 不直接拼 SQL；服务层处理业务，仓储层处理持久化；增加数据库迁移和事务提交／回滚。 |
| 第7天 | 联调与复盘 | 完成 API 集成测试；检查重复提交、非法金额、账户不存在等情况；写一段项目说明。**周验收**：启动服务后，可以创建交易、查询交易并通过鉴权访问报表接口。 |

本周需要能口头回答：

- 为什么脚本式代码难以维护？
- 服务层和仓储层分别解决什么问题？
- JWT 被盗后有什么风险，为什么还需要过期时间？
- POST 重复提交如何防止产生重复交易？
- 同步接口什么情况下会阻塞，是否真有必要全部改成异步？

## 三、第二周：SQL、数据库调优与 ETL／ELT

目标：能设计可靠的数据表、写出报表 SQL，并解释性能问题。

| 天数 | 学习重点 | 实操任务与验收标准 |
|---|---|---|
| 第8天 | 表设计与约束 | 建立客户、账户、交易、批次表；设计主键、外键、唯一约束、非空约束和金额精度；交易号必须唯一。 |
| 第9天 | 进阶 SQL | 练习 JOIN、GROUP BY、CASE、CTE、窗口函数；完成“每日交易汇总”“客户累计交易额”“账户交易排名”三份报表。 |
| 第10天 | SQL 性能调优 | 使用 `EXPLAIN ANALYZE` 对比优化前后执行计划；练习组合索引、覆盖查询、避免对索引列随意套函数、深分页改游标分页。 |
| 第11天 | 事务与一致性 | 演示转账时扣款与入账必须同时成功或失败；理解事务隔离、脏读、不可重复读、幻读；处理唯一键冲突和死锁的基本思路。 |
| 第12天 | ETL／ELT 设计 | 画出 Raw→Clean→Mart 流程；设计批次号、来源、加载时间、处理状态；比较全量、增量、水位线和拉链保存的适用场景。 |
| 第13天 | 多源数据集成 | 编写 Python 管道，读取 CSV 和 JSON；统一字段、时间格式、币种和金额类型；脏数据进入隔离表，不能让一条坏数据拖死整批任务。 |
| 第14天 | 可靠性与数据质量 | 增加空值、重复、参照完整性、金额非负等检查；记录输入／成功／失败数量及金额核对；同一批次重复运行不得产生重复数据。 |

**周验收必须包含四项证据：**

1. 同一份文件重复导入，结果仍保持一致。
2. 脏数据可以被隔离和追踪。
3. 报表结果能够与源数据对账。
4. 至少保留一组 SQL 优化前后的执行计划和真实耗时。

本周重点理解：数据管道通常不要轻率承诺“绝对 exactly once”，更常见的是**至少一次处理＋幂等写入＋业务去重**。

## 四、第三周：PySpark 与完整数据管道

目标：满足“Kafka、Flink、Spark 至少一种”的要求。本月选 Spark 学深一点，Kafka 只了解定位。

| 天数 | 学习重点 | 实操任务与验收标准 |
|---|---|---|
| 第15天 | Spark 基础 | 理解 Driver、Executor、DataFrame、Transformation、Action；运行本地 PySpark；弄清哪些操作不会立即执行。 |
| 第16天 | 数据处理 | 完成过滤、连接、聚合、去重、空值处理、日期处理；避免在数据驱动代码中随意 `collect()`。 |
| 第17天 | Spark 清洗与汇总 | 将第二周部分清洗和报表任务改写为 PySpark；输出每日交易汇总、客户交易统计和异常交易清单。 |
| 第18天 | 性能基础 | 查看执行计划；理解 Shuffle、分区、宽依赖；练习列裁剪、提前过滤、合理缓存、广播小表 Join；不盲目追求分区数量。 |
| 第19天 | 批流差异与 Kafka 概念 | 理解 Topic、Partition、Consumer Group、Offset，以及重复消费和乱序；只画“Kafka→流处理→数据库”的架构，不必强行加入项目。 |
| 第20天 | 系统整合 | 串联“文件导入→质量检查→Spark 汇总→结果入库→API 查询”；为每个批次保存开始时间、结束时间、状态和错误信息。 |
| 第21天 | 故障演练 | 人为制造文件缺失、字段变更、数据库中断、任务重复执行；确认系统能报错、重跑和恢复，而不是悄悄产出错误报表。 |

**周验收：**

- 用一批较大的模拟数据运行 Spark 作业。
- 能解释为什么发生 Shuffle，以及一次优化为什么有效。
- 任意批次都能回答：读了多少、成功多少、失败多少、输出多少、金额是否对平。
- 微服务只需能讲清服务边界、鉴权、超时、重试和分布式追踪，不必为了岗位描述强行拆成多个服务。

## 五、第四周：云平台、金融场景与面试冲刺

### 第22～25天：补齐加分项并封版项目

**第22天：云平台映射**

选择以下一条路线，不要两边同时学：

- Azure：Blob／Data Lake 存储，ADF 负责编排与复制，Databricks／Spark 负责转换，数据库承载报表。
- 阿里云：OSS 存储，DataWorks 负责调度集成，MaxCompute 负责计算，API 服务查询结果。

产出一张架构图，标清数据落点、调度关系、失败重跑和权限边界。

**第23天：云方案演练**

有账号和免费额度时，只做一个最小数据复制或 Spark 作业；没有条件就在本地完成，并写清楚云上组件如何替换。不要为了跑通教程产生高额费用。

**第24天：金融数据场景**

用合成数据实现简单练习规则，例如大额交易、短时间高频交易、账户信息与交易缺失关联。重点学习：

- 客户、账户、交易之间的数据关系。
- 监管报表的数据 lineage，即结果能追溯到来源和批次。
- 数据权限、敏感字段保护、审计日志和保留期限。
- 规则结果必须能够解释，不能只输出一个无依据的风险分数。

**第25天：项目封版**

整理启动脚本、依赖、测试、示例数据和 README；用 Docker Compose 启动 PostgreSQL 等基础组件。README 至少包含：

1. 架构图。
2. 启动步骤。
3. API 示例。
4. 数据管道运行方式。
5. 幂等和质量保障设计。
6. 已知限制及下一步优化。

### 第26～30天：面试训练

| 天数 | 训练内容 | 当日成果 |
|---|---|---|
| 第26天 | Python／API 面试 | 回答 OOP、生成器、GIL、可变默认参数、异常处理、鉴权、幂等、分页等问题；完成一次30分钟现场编码。 |
| 第27天 | SQL／ETL／Spark 面试 | 不看答案写窗口函数和汇总 SQL；解释执行计划、增量加载、重复数据、迟到数据、Shuffle 和广播 Join。 |
| 第28天 | 系统设计 | 用“需求→数据源→存储→管道→质量→API→安全→监控→恢复”的顺序，在15分钟内讲完整项目。 |
| 第29天 | 模拟面试与简历 | 录一遍自我介绍和项目介绍；简历只写自己真正实现的内容，性能提升必须填真实测量值。 |
| 第30天 | 最终验收 | 从空环境启动项目，演示导入、异常隔离、Spark 处理、报表查询和鉴权；整理薄弱点，开始投递。 |

## 六、最终验收清单

月底不要求“所有题都会”，但至少应达到：

- **Python**：代码有分层、类型、日志、异常和测试，不是单个长脚本。
- **API**：能解释 REST 设计、状态码、JWT、权限和幂等。
- **SQL**：能独立写报表查询，并通过执行计划说明一次优化。
- **ETL**：支持增量、重跑、去重、质量检查、异常隔离和对账。
- **Spark**：能完成真实转换作业，并解释 Shuffle 与分区。
- **云平台**：能画出所选平台的数据链路，而非只背产品名。
- **项目表达**：能在10分钟内讲清业务问题、技术选择、故障处理和实际结果。

如果时间不够，优先保留 **Python／API、SQL、ETL、PySpark 和完整项目**；Kafka、微服务、跨云迁移和金融规则都降为架构层面的了解。这样比每个技术都看完几节视频、却没有可演示成果，更贴近这份岗位的要求。
